# database_design

用于设计、评审或重构数据库模型、表结构、索引、迁移与数据访问层。重点保证数据模型清晰、约束完整、查询可维护、迁移可控，并能与当前 Go / GORM 项目风格保持一致。

## 核心原则

- 先建模业务实体与关系，再落表结构；不要从临时接口字段直接反推数据库。
- 数据库负责保证关键一致性：主键、唯一约束、非空、外键或等效应用约束必须明确。
- 表结构要可演进；新增字段、改类型、拆表、迁移数据都需要考虑兼容和回滚。
- 优先使用清晰、稳定、可查询的字段，不把复杂业务状态塞进不可检索的 JSON 字符串。
- 安全字段与展示字段分离，例如认证信息、个人资料、token / session 不混放在一张大表里。
- 设计时同时考虑读写路径、并发冲突、索引成本、备份恢复和数据保留策略。

## 命名规范

- 表名使用小写 `snake_case`，优先表达业务资源：`auths`、`users`、`tokens` 或明确约定的单数表名。
- 字段名使用小写 `snake_case`，与 GORM `column` tag、JSON 字段保持可追踪关系。
- 主键字段命名要稳定；业务唯一键可用 `user_name`，系统内部键可用 `id` / `uuid`。
- 布尔状态优先使用语义明确的字段名，例如 `is_active`、`is_initialized`；如果使用 `int` 表示状态，要说明取值含义。
- 时间字段统一命名：`created_at`、`updated_at`、`deleted_at`、`login_at`、`expires_at`。
- 避免拼写错误进入持久化字段；一旦已上线，修正字段名需要迁移方案。

## 表与关系建模

- 一张表只表达一个核心实体或关系，不把认证、资料、令牌、审计日志全部混在一起。
- 一对一扩展信息可拆表，例如当前项目的 `Auth` 与 `User` 通过 `user_name` 关联。
- 一对多关系必须明确外键方向，例如一个用户可拥有多个 token：`tokens.user_name -> users.user_name`。
- 多对多关系使用中间表，并给中间表设置联合唯一约束。
- 枚举和状态字段要定义合法取值、默认值和状态流转规则。
- 历史记录、审计日志、会话 token 等增长型数据要提前考虑清理策略和归档策略。

## 主键与唯一约束

- 每张表必须有明确主键；主键应稳定、不可复用、不可频繁变更。
- 用户名、邮箱、token 等业务唯一字段必须设置唯一约束，而不是只依赖应用层查询。
- 联合唯一约束用于表达业务不可重复规则，例如 `(user_name, role_id)`。
- 外部可见 ID 与内部主键可分离；不要暴露自增 ID 时，可使用 UUID 或业务编码。
- token、session、密码散列等敏感唯一字段不应在日志中完整输出。

## 字段类型与默认值

- 字段类型以业务语义为准：金额使用定点数，时间使用时间类型或统一格式，状态使用小整数/枚举。
- 字符串字段要明确最大长度，特别是用户名、邮箱、手机号、token、备注。
- 必填字段设置 `NOT NULL` 或应用层等效校验；可空字段要说明 `NULL` 与空字符串的差异。
- 默认值必须有业务意义，避免用伪造手机号、邮箱等占位数据长期落库。
- 密码只保存强哈希结果，不保存明文、可逆密文或固定盐生成的弱哈希。
- 时间字段建议使用 UTC 或明确时区策略；当前项目使用 RFC3339 字符串时，要保持全局一致。

## 索引设计

- 为高频查询条件建立索引，例如 `user_name`、`token`、`alive`、`created_at`。
- 联合索引顺序按查询条件选择性和常用查询模式设计，例如 `(user_name, alive)`。
- 唯一索引既是性能优化，也是数据约束；不要只为查询而忽略业务唯一性。
- 避免给低选择性字段单独建过多索引，例如纯布尔状态字段通常需要与其他字段组合。
- 写入频繁的表要控制索引数量，索引越多写入成本越高。
- 新增索引前先明确目标 SQL / GORM 查询路径，避免“猜测式加索引”。

## 迁移与版本管理

- 表结构变更必须可重复执行、可审计，并尽量支持灰度发布。
- 开发早期可使用 GORM `AutoMigrate`，但生产环境重要变更建议使用显式迁移脚本。
- 破坏性变更采用分阶段策略：新增兼容字段 → 双写/回填 → 切读 → 清理旧字段。
- 数据迁移要考虑批量大小、事务边界、失败重试和回滚方案。
- 字段重命名、类型收窄、唯一约束新增前，需要先清理历史脏数据。
- 迁移后同步更新模型 struct、接口文档、测试数据和初始化逻辑。

## 事务与一致性

- 多表写入必须使用事务，例如创建认证记录同时创建用户资料。
- 事务范围保持短小，只包含必须原子提交的数据库操作。
- 并发敏感操作要考虑唯一约束、行锁、乐观锁或幂等键。
- 先依赖数据库约束兜底，再用应用层预检查提升错误提示友好度。
- 对外部调用、文件操作、网络请求不要放进长事务里。
- 失败时返回明确错误并记录上下文，避免半成功状态无人感知。

## 安全与隐私

- 敏感字段最小化存储：密码、token、手机号、邮箱、审计信息按需保存。
- 密码使用专用密码哈希算法，例如 bcrypt / argon2；不要只用普通 SHA256 加固定盐。
- token 只在必要时保存，建议保存哈希值或可撤销标识，并设置过期时间。
- 个人信息字段需要考虑脱敏展示、访问权限和删除/匿名化策略。
- 数据库错误不直接返回给 API 调用方；内部日志也要避免打印敏感字段。
- 配置中的数据库账号、密码、DSN 不写入代码和文档示例的真实值。

## 查询与数据访问层

- 数据访问函数以业务语义命名，例如 `UserInfoByToken`、`GetUserAllAliveToken`。
- 查询函数只返回调用方需要的数据，避免把认证表完整暴露给上层响应。
- 使用参数化查询或 ORM 条件构造，禁止字符串拼接 SQL 输入。
- 需要区分“未找到”和“数据库错误”，便于 API 映射为 `404`、`401` 或 `500`。
- 高频链式查询可考虑 join 或预加载，避免循环内 N+1 查询。
- 返回值约定要稳定：布尔结果、实体指针、错误三者语义不要混乱。

## GORM 实现建议

- 模型 struct 的 `gorm` tag 必须表达列名、主键、唯一索引、索引和必要约束。
- 对跨表关系可增加显式外键 tag，或在技能输出中说明为何由应用层维护。
- 创建关联数据时使用 `db.Transaction(func(tx *gorm.DB) error { ... })`。
- 更新部分字段时优先使用 `Select` / `Updates(map[string]any)`，避免零值字段被意外忽略或覆盖。
- 查询 token 等唯一记录时使用 `First` 并处理 `gorm.ErrRecordNotFound`。
- MySQL 与 SQLite 兼容时，避免使用某一数据库独有语法；必须使用时要注明驱动差异。

## 当前项目关注点

- `Auth`、`User`、`Token` 已拆分为认证、用户资料和令牌三类模型，后续设计应保持职责分离。
- `Auth.UserName` 与 `User.UserName` 是跨表关联键；创建用户时应保证两表写入的原子性。
- `Token.Token` 是唯一敏感凭证；查询、日志、响应和持久化策略需要重点保护。
- `created_at`、`updated_at`、`login_at` 当前以 RFC3339 字符串保存；新增时间字段应保持一致或明确迁移为数据库时间类型。
- `alive` / 初始化状态等整数状态字段应补充取值说明，避免后续出现魔法数字。
- 如果继续使用 GORM `AutoMigrate`，仍需记录结构变更意图和兼容影响。

## 评审清单

- [ ] 是否明确了实体、关系、生命周期和数据所有者？
- [ ] 每张表是否有主键、必要唯一约束和必要索引？
- [ ] 字段类型、长度、默认值、可空性是否符合业务语义？
- [ ] 多表写入是否需要事务，是否避免半成功状态？
- [ ] 高频查询是否有索引支撑，索引数量是否可控？
- [ ] 敏感字段是否最小化存储并避免明文/日志泄露？
- [ ] 迁移路径是否可重复、可回滚、可兼容旧版本？
- [ ] GORM model、数据库迁移、API 响应和文档是否同步？

## 输出模板

当用户要求设计或评审数据库时，优先按以下格式输出：

```text
数据库设计建议：

- 实体与关系：<核心表、关联关系、生命周期>
- 表结构：<表名 + 关键字段 + 类型/约束>
- 主键与索引：<主键、唯一约束、查询索引>
- 写入一致性：<事务、幂等、并发控制>
- 安全策略：<敏感字段、脱敏、权限>
- 迁移影响：<是否需要迁移脚本、回填、兼容步骤>
```

## 示例

用户、认证与 token 设计：

```text
auths
- user_name: string, primary key, unique
- hashed_passwd: string, not null
- created_at: RFC3339 string
- login_at: RFC3339 string, nullable/empty
- is_initialized: int/bool

users
- user_name: string, primary key, unique, references auths.user_name
- nick_name / phone / email / department / position / location: profile fields

tokens
- token: string, primary key, unique
- user_name: string, indexed, references users.user_name
- created_at / updated_at: RFC3339 string
- alive: int, indexed with user_name

关键建议：创建 auths + users 使用事务；tokens 增加过期时间或清理策略；敏感 token 日志脱敏。
```
